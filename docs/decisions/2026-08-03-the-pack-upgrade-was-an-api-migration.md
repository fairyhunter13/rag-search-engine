# The "zero new code" pack upgrade was an API migration, and only the tests said so

**2026-08-03** · `EXTRACTOR_REV` e8 → e9 · `tree-sitter-language-pack` 1.12.1 → 1.14.0

The plan ranked this item **#4** and costed it as *"a dependency bump; **zero new code**"*, with the
regenerated capability matrix as the review artifact. The matrix was regenerated, the diff was read,
and it was **clean and strongly positive** — of the 306 pre-existing languages, **0 regressed, 0 were
removed, 65 were added and 36 gained capability**, landing precisely on the fleet's dark mass:

| | 1.12.1 | 1.14.0 |
|---|---:|---:|
| languages | 306 | **371** |
| highlights | 237 | 319 |
| tags | 48 | 71 |
| injections (of which static) | 110 (75) | 157 (111) |
| locals | 81 | 108 |
| no query files | 66 | **51** |

- **php** `6 recorded` → `1 injections` — gains highlights **and** injections. That is the
  `injections.scm` absence §1g of the plan measured against 746 `*.tpl.php` templates.
- **typescript** and **tsx** `6 recorded` → `4 highlights`, gaining tags and locals.
- **vue** → rung 1. **vimdoc** (390 files, 100% dark) → rung 1.

**And on that evidence the upgrade was still broken, in a way the matrix cannot see.** The fast live
suite came back **43 failed / 826 passed**.

## What actually changed

`tree_sitter_language_pack.api.get_parser` used to return the pack's own Rust-backed parser, whose
`Node` is a distinct type from `tree_sitter.Node` and exposes **method-style** accessors. In 1.14.0
it returns a real `tree_sitter.Parser` producing real `tree_sitter.Node`s, where the same accessors
are **properties**. The pack still exports a native `Node`, so the type did not vanish — it simply
stopped being what `get_parser` hands back.

Every method-style call therefore raised `TypeError: 'Node' object is not callable` inside an
`except Exception` and returned the empty answer:

| was | is | sites |
|---|---|---:|
| `.kind()` | `.type` | 10 |
| `.named_child_count()` | `.named_child_count` | 5 |
| `.root_node()` | `.root_node` | 3 |
| `.byte_range()` → `.start`/`.end` | `.start_byte` / `.end_byte` (it is now a plain tuple) | 7 |
| `.start_position().row` | `.start_point[0]` | 6 |
| `parser.parse(str)` | `parser.parse(bytes)` | 2 |

The last row is the one with no type error to raise: py-tree-sitter requires bytes, so the native
parser's tolerance of a `str` was load-bearing without anyone knowing it.

## Why the totals line did not catch it

The matrix is generated by asking the *pack* what query files each grammar ships. It never parses a
file through this repo's extractor, so it is a tripwire for **node-type churn in the grammars** and
is blind to a change in the **binding** that reads them. Both are "the pack upgraded"; only one is
what the artifact measures. The plan's verification note — *"the totals line is the tripwire… a query
silently matching nothing looks identical to a language with no symbols"* — was right about the
failure mode and wrong about which instrument sees it.

## The shape of the failure, which is the part worth carrying

`process()` kept working. Symbol extraction on the structure rung — the primary path — was
**unaffected**, so a spot check of "does python still extract" passes. What broke was everything
reading the raw AST: the generic walk, the highlights and data rungs, the embedded/injection blocks,
`_error_byte_ratio`, and **all call-edge extraction**. Files fell through to `unparsed`, and
`test_ts0_same_file_calls_become_edges` — two functions, one call, one file — produced **zero edges**.

So the degradation was **partial and silent**: the loudest signal available to a human doing a quick
check was green. Only the suite, which asserts rung-by-rung and edge-by-edge across five languages,
distinguished "extracts" from "extracts everything it used to". This is the third entry in this
directory whose lesson is that the cheap check and the real check disagree, and the first where the
cheap check was a *generated document* rather than a test.

## The daemon's stored graphs went to zero edges in the meantime

`_code_fingerprint` re-reads fingerprinted modules on every call, so the running daemon picked up the
edited `extractor.py` **on save** and re-derived with the broken accessors. For the length of the fix
window it wrote real stores holding **0 edges** — `test_pipeline_all_stages_rse_repo` was the last
red test after the code was correct, and it was reporting the *data*, not the code. The re-derive
under `e9` is what repairs it, which is exactly what the stamp is for.

## What this changes

- **`EXTRACTOR_REV` moved to `e9` for a reason S3 already anticipated** and this incident makes
  concrete: a dependency version is invisible to `_code_fingerprint`, which hashes source modules.
  Without the bump the fleet keeps serving edges the installed pack no longer produces.
- **A pack upgrade is a code change until the suite says otherwise.** The capability matrix stays as
  the grammar-churn detector it is good at being; it is not upgrade sign-off. Nothing here argues for
  a new gate — the existing suite caught it in one run, on the first try, with 43 named failures.
- The plan's `#4` line — *"a dependency bump; zero new code"* — is corrected in place. The coverage
  win it predicted is real and is now shipped; the cost estimate was wrong by one API migration.
